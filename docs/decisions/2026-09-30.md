# Decisions — 2026-09-30

## pure reference metric before storage queries

- **Choice:** define `hard-braking/v1` over canonical samples in a pure Python transform. Return one result per source drive, with independent episode and exposure outputs and source-key lineage. Only adjacent intervals of at most one second qualify. A rate is episodes per 100 km of valid distance; no eligible intervals and zero distance have distinct undefined states.
- **Why:** the frozen tiny oracle can verify episode and distance arithmetic before SQL or API aggregation adds more failure modes. Sorting by event time with a sequence-order check makes results independent of input ordering while rejecting contradictory source data.
- **Alternative:** calculate the first result directly in ClickHouse. That would serve large scans sooner but make the initial metric harder to test independently of storage replay and query grain.
- **Limit:** these generated drives do not establish real-fleet prevalence or event completeness. A later cohort rate must sum counts and exposure before division and use guarded logical sample reads.

## production bridge as a standing learning feature

- **Choice:** give every implemented concept a production-bridge card, and make a three-part *bridge check* (FleetLens mechanism, production pattern, one difference) the preferred evidence for moving a ledger row to demonstrated. New walkthroughs must add or update their card.
- **Why:** interviewers assess whether a candidate can generalize from a project to production systems. Tying each concept to a named pattern and its guarantee also makes FleetLens's own limits explicit.
- **Alternative:** a standalone glossary of production terms. It would be shorter, but it would not tie terms to FleetLens code or require Bryan to explain the difference, so it could encourage name-dropping without understanding.
- **Limit:** production patterns are described from public, general industry practice, not Tesla internals or FleetLens measurements. Cards for M2–M5 concepts are deliberately deferred until the code exists.
- **Revisit when:** a card's "In FleetLens" line no longer matches the code, or bridge-check answers show the three-part rubric is not distinguishing explained from demonstrated.

## guarded one-statement snapshot read for metrics

- **Choice:** group raw ClickHouse rows by source key in one dataset/snapshot-scoped statement. Carry a snapshot-wide distinct-payload conflict count and logical-key count on each returned row, then reject conflicts and over-limit snapshots before constructing canonical samples. The initial bound is 1,000 samples by default, hard capped at 10,000; cohort output also caps drives. The drive summary first guards the bounded snapshot, then selects a drive. Render stored event times explicitly in UTC.
- **Why:** the existing logical view omits conflicted keys, and a separate conflict check followed by a read could see different writes. The grouped statement collapses identical replay rows while making conflicts visible in the same query result. Cohort rates sum event counts and valid distance before division.
- **Alternative:** maintain a materialized conflict-free table and query it directly. That needs a durable revision and recovery policy beyond this local increment; a direct unguarded view read would make changed payloads disappear.
- **Limit:** the database still groups all rows for a selected snapshot even though the response is bounded. Safe selector characters are narrower than the generic Python identity contract. No distributed consistency, query latency, real-source semantics, or event-ascertainment correction is claimed.

## preserve source-snapshot integrity before publishing a stored rate

- **Choice:** append a load receipt after each raw sample insert, recording dataset/snapshot, source-file hash, and input/accepted/rejected counts. The guarded read requires one source-file hash across all selected raw rows and compatible receipts. It marks a snapshot incomplete and leaves rates undefined when a receipt is missing, counts disagree with logical rows, or any source row was rejected.
- **Why:** a same-key payload guard alone misses a second source file that reuses a snapshot ID with disjoint keys. Raw rows alone also cannot prove a complete source after quarantine or an interrupted insert. An isolated reviewer probe reproduced a changed cohort rate from mixed file hashes despite all previous replay tests passing.
- **Alternative:** enforce snapshot identity on every load using a transactional registry. That would need a coordinator or database with a uniqueness transaction; this local ClickHouse slice keeps append-only evidence and detects conflicts at read time.
- **Limit:** raw insert and receipt insert are separate operations, so a crash can leave rows without a receipt and the rate undefined until a safe replay. This is a local protocol, not a distributed transaction or protection against direct database tampering. An all-rejected source has no accepted row from which the current load API can recover dataset/snapshot identity; its quarantine report remains the source accounting record.
- **Revisit when:** larger loads, concurrent correction workflows, or real sources require a durable ingest ledger and explicit authoritative revisions.

## serve fixed local metric routes with standard-library WSGI

- **Choice:** expose only cohort, drive, and event-detail GET routes over the guarded stored summaries. Cap samples and drives, use stable JSON errors, and bind the local server to loopback. Keep the API in the Python standard library for this first demonstration.
- **Why:** the explorer needs a narrow contract with source lineage and completeness status, not arbitrary SQL. WSGI lets request tests run without opening a port and keeps the installed package's runtime dependencies unchanged.
- **Alternative:** FastAPI would provide declarative request models and generated OpenAPI, useful when the endpoint set or external consumers grow. It adds a runtime dependency and a larger serving stack before this local contract needs them.
- **Limit:** this synchronous server has no authentication, pagination, cross-request snapshot transaction, or measured concurrent capacity. A published deployment would require a separate security and operating design.
- **Revisit when:** endpoint count, client diversity, measured latency, or deployment requirements justify a framework or different server.

## use explicit vehicle strata and one local demo runner

- **Choice:** aggregate drive metrics by canonical `vehicle_id`, summing episodes and valid metres before division. Put the fixed fixture, guarded load/read measurements, API, and explorer behind one `fleetlens-demo` command from a prepared repository. Keep metric computation in Python; the browser displays API results and source lineage.
- **Why:** vehicle ID is an actual source field, so strata need no scenario inference from a drive name. One command makes the small source-to-screen demonstration repeatable and makes physical-versus-logical replay behavior visible.
- **Alternative:** infer scenario categories from generated drive IDs and calculate/display those rates in the browser. That would depend on a naming convention and duplicate metric semantics across clients. A durable scenario field can be added with a new contract version when useful.
- **Limit:** two invented vehicles are illustrative, not a representative fleet. The demo requires a local ClickHouse service and installed npm dependencies, and its timings are tiny single-host observations.
- **Revisit when:** a real validated source adds meaningful strata, or measured workload calls for persisted aggregates and a stronger serving process.
